# Bounded regression review - current through 2026-11-18

This review starts from `1c0768c` and inspects the committed remaining-work repairs plus identified local follow-ups. Source was re-read on November 18; a checked-in test definition is not an execution result. It is a targeted code and caller review, not an exhaustive security audit or proof that every entry point works. Current outcomes, commits, and final validation belong in [remaining work status](remaining-work-status.md).

## Findings and remedies

| Contract | Evidence and trigger | Remedy and regression evidence |
| --- | --- | --- |
| Derived search consistency | `AppSearchBackedSearchIndexRepository` previously locked session creation only. Rebuild could clear documents while incremental writers ran; nonempty namespaces could represent an interrupted partial rebuild. | One owner serializes mutations, session creation/reset, rebuilds and ready-index reads. Search/suggestion reads use `tryLock`: cold or busy owners return immediately to existing Room fallback instead of waiting for session creation/rebuild. A coherent Room snapshot releases its transaction before AppSearch writes. Readiness requires a successful complete rebuild; existing namespaces alone do not establish readiness. Failed batches reset the session/readiness and coalesce automatic reconciliation. Missing-ID removal is idempotent. Twelve `SearchIndexRecoveryTest` definitions cover partial batches, queued writes/overlapping rebuilds, delete/archive, cancellation after clear, fresh-owner recovery, bulk reads, canceled ready reads, autonomous retry/coalescing/exhaustion, session reopen, cold fallback and fallback during a held rebuild. Execution counts and latest outcomes belong in the ledger/final validation report. |
| Rebuild query growth | `rebuildAll()` previously called `getByWebsiteId()` for every website. | One `IconCacheDao.getAll()` map replaces the per-row reads. The regression measures icon read counts at 100, 1,000, and 5,000 links and checks preserved cached URI mapping. Timing observed while Gradle is running is not a valid steady-state performance comparison. |
| Unsafe capture validation | Production `normalize()` skipped the blocked-scheme check that existed only in strict normalization. The previous test explicitly allowed `javascript:` capture. | Both modes reject `file`, `content`, `data`, and `javascript`, including mixed case. Existing supported custom schemes remain storable. Parameterized loops in `UrlNormalizerTest` cover both modes. Fetching and external opening already rejected these destinations; no exploit or code execution is claimed. |
| Metadata refresh preservation | A generated fallback could overwrite saved title and icon choice through the sole `WebsiteDao.updateMetadata()` caller. A response could also arrive after an edit or replacement of the same ID. | Preserve nonblank saved titles, explicit custom/emoji choices, and all existing metadata on generated fallback. Re-read and compare the current row inside the update transaction; skip a changed or deleted row. `MetadataRefreshPreservationTest` exercises fallback, successful refresh, edits, and ID-preserving replacement without network access. The metadata worker currently has no discovered enqueue caller; this was a latent use-case/worker defect. |
| Warm shortcut activation | `ComponentActivity.onNewIntent()` dispatches registered listeners. Navigation 2.9.8 restarts the task for a deep link with `NEW_TASK` and no `CLEAR_TASK`, cloning the intent before later code can consume its activation extra. | Consume the shortcut activation before `super.onNewIntent()`. Verify warm routing, recreation, and stable shortcut IDs with `ShortcutActivationTest`. Resolved Navigation source confirms the task-restart branch; final runtime results belong in the ledger. |
| Dashboard restoration race | The debounced query callback could mark default empty dashboard data loaded before the first Room/DataStore combined emission. New stale-ID reconciliation could consequently discard restored sheet targets. | `DashboardViewModel.hasLoadedDashboard` is set only by the combined source emission, and `publishDashboard()` returns before that first emission. The debounced query therefore cannot reconcile restored targets against default empty data. This is implemented in `24fda77`; a dedicated delayed-source barrier regression remains distinct from recreation/process-death evidence. Recreation alone does not prove saved-task process death. |
| Repeated export result | A repeated save callback while the first export write is running could find no `ReadyToSave` package, reset status to idle, and unlock backup controls during the write. | `onSaveExportToUri()` ignores states other than ReadyToSave/Idle and synchronously switches to Building before launching output. A repeated callback during the write cannot reset the status or unlock controls. Idle still reports an expired in-memory export package. `SettingsOperationTest` exercises rapid import ownership; it does not independently prove repeated export callbacks or picker process-death expiration. |
| Recovery and replacement outcome | Exports and pre-restore recovery previously shared one replaceable slot; snapshot/Room/preferences/index publication crosses separate stores. | `aa726bf` separates exports from two-generation recovery, validates complete generations, preserves the newest verified source and incomplete operations, and gives AtomicFile recovery precedence over manual deletion. PREPARED fingerprints precede replacement; a NonCancellable COMMITTED marker follows Room before preferences/index. Explicit reconciliation releases only durable commit evidence or conservative canonical-state matches; unknown outcomes remain protected. `BackupRestoreTest`, `RecoveryBackupStoreTest`, `BackupBoundaryTest`, `BackupProviderTest`, and JVM output/asset tests exercise the responsible boundaries. No automatic destructive restore retry is added. |
| Portable images and cleanup ownership | Imported JSON paths/grants cannot establish access. Regenerable cache paths are not portable; image files need publication/rollback ownership. | Existing envelopes add bounded, checksummed, deduplicated PNG/JPEG/WebP assets and generated app-private destinations. All assets validate/decode before publication/Room replacement; rollback checks authoritative references before removing files. Source/destination storage and cross-package fixture tests are separate from ordinary production-library tests. Grant-backed foreign images remain deliberately omitted/count-warned. Final review identified URI-spelling-sensitive cleanup (`file:/` versus `file:///`). `72de7d2` compares canonical owned-file identities; `BackupBoundaryTest.exportPreservesOwnedImageReferencedByEquivalentAndroidUri` passed export/reopen, image-byte preservation and orphan deletion on API 36. Foreign paths are not opened by cleanup. |
| Staged export publication | `BackupFileManager.stageBackup` relied on `AtomicFile.finishWrite` returning. A blocked destination can make platform rename fail without throwing. | `3ce85bd` verifies bounded published content before returning a path. A blocked `.new` preserves the previous staged export. A blocked base produces a reported failure. The same patch tests a separate valid-image publication failure before Room commit, verifies the original library and image bytes after reopen, and leaves the owned blocker untouched. |
| Duplicate choices in optimized release | One task-owned custom-scheme URL, an Inbox record with a note/priority/follow-up, and one task-owned destination category. | November 21 UI smoke exercised cancel, move and merge with a conflicting incoming note. An app restart and read-only Room copy verified a single active record, intended category and original fields. The opened destination record and category were verified before cleanup. |
