# Backup format and recovery

LinkNest writes format-v2 JSON envelopes containing kind `linknest.backup`, metadata, and base64-encoded GZIP snapshot data. SHA-256 covers compressed bytes. This detects accidental corruption; it does not authenticate a file and is not encryption. Legacy plain snapshots and supported database schemas 1 through 6 remain readable. Newer schemas are rejected.

Encoded input and expanded snapshot text each have a 32 MiB character limit. Streaming external reads stop at that limit. The serializer also rejects envelopes exceeding the import limit. Snapshots contain categories, websites, tags, relationships, mappings, saved filters, integrity events, recent queries and optional preferences. Enum/database identifiers are unchanged. The current device's backup-folder preference and permission grant are never replaced from JSON.

## Replacement boundary

Import previews incoming/current counts and requires replacement confirmation. The current library is serialized and verified as a recovery generation before replacement. Room changes are transactional. Custom image bytes are validated and published first, then only generated local image URIs enter the Room transaction. Failed publication or Room replacement preserves original rows; cleanup checks authoritative Room references before deleting operation-created image files. Preferences and AppSearch run after Room commit. Their ordinary failures report that the library was replaced with finalization warnings. Cancellation propagates before and after commit; it is never converted into success or a claim that the original library survived.

A cancellation or process interruption can leave a protected recovery generation whose operation outcome needs reconciliation. Room and files/DataStore/AppSearch are not one cross-store transaction. Before replacement, the recovery manifest records canonical before/expected fingerprints and PREPARED phase. After Room returns, a NonCancellable finalization block durably records COMMITTED before preferences/index work. Failure to write that post-commit marker reports a committed replacement warning and retains protection; it never becomes a pre-commit error. A process can still die between Room commit and marker publication, so fingerprints reconcile that interval without replaying replacement.

## Recovery retention

Exports use only `latest-backup.json`. Recovery uses generated `recovery-<UUID>.json` files and an AtomicFile-published `recovery-index.json` manifest containing version, generation name, whole-file SHA-256, creation time, and completion state. Recovery generations contain their own portable images. Ordinary exports and export cleanup cannot overwrite or delete recovery generations.

The policy retains two published generations of at most 32 MiB encoded bytes each. During publication a third generation can temporarily exist (96 MiB payload ceiling, excluding filesystem/manifest overhead). Old eligible generations are pruned only after a replacement generation and manifest are durable and verified. The newest verified prior recovery and every incomplete operation remain protected. Identical pending snapshots, ignoring export time, reuse their protected generation. Known pre-commit failure and successful restore release operation protection, while retaining the generation under the ordinary two-generation policy. Cancellation and unknown outcomes retain protection. Settings provides explicit Reconcile interrupted restores: the repository reads current authoritative Room/media state, then releases only generations with a durable COMMITTED marker or fingerprints matching staged/imported content. Canonical fingerprints sort records/relationships/assets and exclude export time, app/schema display metadata, preferences, regenerable cache records, omitted-image counts and remapped local URI strings; portable image bytes/IDs and personal record fields remain included. Omitted or unrepresented custom references prevent fingerprint-based original-state equality, even if portable record fields match; current unrepresented references also prevent imported-state equality. A recorded COMMITTED phase remains direct commit evidence. Neither match means UNKNOWN: protection remains, even after subsequent edits. If protection exhausts the budget, staging fails before replacing records; it never removes the only verified recovery to make space. Truly unknown outcomes still require an explicit verified-external-export/acknowledgement resolution flow; no unsafe automatic expiry is implemented.

Recovery discovery validates manifest-controlled filenames, hashes, envelope integrity and snapshot structure; a corrupt newest payload falls back to a verified older generation. A malformed unrecoverable manifest blocks replacement rather than guessing among files. AtomicFile gets the first chance to restore `.bak` and discard interrupted `.new` writes. Legacy staged-export discovery opens exactly `latest-backup.json` with AtomicFile recovery; arbitrary similarly named files are not selected by timestamp.

Settings distinguishes Import last export from Restore recovery snapshot. Both preview and require replacement confirmation. The source recovery remains protected while another recovery is staged for the current library. External exports remain recommended for device loss.

## Portable custom images (additive media version 1)

The snapshot adds `mediaVersion: 1`, `assets`, `omittedCustomImages`, and optional website `customIconAssetId`. Each asset has `id` (lowercase SHA-256 of decoded file bytes), `mimeType` and base64 `data`. Duplicate byte-identical images share one ID. No asset filename/path is accepted from JSON. Legacy custom URI/cache fields are read only for compatibility and are never opened during import.

Exports include only canonical files directly inside this installation's app-owned `icon-cache` or `backup-media` directory. Foreign file paths and content URIs are omitted and counted for preview/reporting; this implementation does not export grant-backed content URIs. Exported custom URI fields are cleared. Regenerable remote caches and their paths are omitted; there are no network downloads during import/export. Existing custom image source preference remains intact, with a local fallback when the image is unavailable.

Limits: 128 assets, 512 KiB encoded-file bytes per image, 8 MiB total file bytes, PNG/JPEG/WebP only, maximum 2048 pixels per side and 4,194,304 pixels per image, and 8,388,608 pixels across assets (approximately 32 MiB decoded RGBA). Before publishing files, import checks IDs/references, duplicate/missing assets, base64 and checksums, byte budgets, actual decoder MIME/dimensions and successful bitmap decoding. Assets cannot provide permissions or traversal names.

Published files use generated app-private `backup-media/asset-<UUID>.image` names. All assets validate before any file or database replacement. Files are fsynced before database references are written. Rollback checks live Room references and removes unreferenced generated files; the next export/import also reconciles abandoned files after restart. A background startup-only cleanup hook is not established. Prior library media is recoverable from retained self-contained recovery snapshots. Unknown files and files outside the owned generated directory are never deleted by media cleanup.

## Regression evidence

`BackupOutputTest` covers successful UTF-8 write/close, null stream and injected write/flush/close failure. `BackupAssetsTest` covers additive compatibility and malformed/oversized asset metadata. `RecoveryBackupStoreTest` covers export independence, restart discovery, corrupt-newest fallback, retention/protection, injected manifest-publication failure AtomicFile legacy/manifest recovery, and durable restart reconciliation of before/after/changed-unknown states. `BackupBoundaryTest` covers post-commit warnings/cancellation, separate isolated source/destination media round-trip without the source file, reopen, media rollback/recovery, malformed decoder input and foreign-path omission. `BackupRestoreTest` covers all backed-up relational tables, preferences, cache preservation on rollback and original transaction failure.

These are test definitions, not execution claims. See the current audit validation report for latest executed counts and failures. BackupProviderTest adds an isolated wrapped DocumentsProvider exercising null streams, revoked access, streamed chunks/truncation, creation/open failures, broken-pipe writes, successful output and cleanup ownership. Pure output tests inject flush/close exceptions at the stream boundary; these are not claims about every real SAF provider. Real provider-specific revocation/creation/close behavior, process interruption at every filesystem phase, grant-backed custom image export and every disk-pressure/restart combination remain distinct from these deterministic checks.
